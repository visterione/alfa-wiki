# Код-ревью мобильного приложения — 01.08.2026

Точка отсчёта: последний коммит мобилки — `daaa8ce ver. 0.02` от **18.03.2026**.
Веб за это время ушёл с `ver. 1.85` до `ver. 6.40` (01.08.2026).
`backend/routes/chat.js` менялся после заморозки дважды: **06.04** (`ver. 2.73`) и **27.07** (`ver. 6.15`) — +408 строк.

Отдельно: папка `mobile/` — самостоятельный git-репозиторий и **не отслеживается** основным
(`?? mobile/` в git status корня). Это осознанно или случайно — стоит решить, иначе мобилка
выпадает из общей истории версий и из деплой-процесса.

## 1. Блокеры (без этого релизная сборка не работает вообще)

### 1.1 Release-сборка Android не сможет сходить в сеть
`src/config.js` → `http://192.168.22.39:9001`.
RN gradle plugin (`AgpConfiguratorUtils.kt:42`) выставляет `manifestPlaceholders["usesCleartextTraffic"] = "false"`
для buildType `release`. Манифест (`android/app/src/main/AndroidManifest.xml:19`) использует этот плейсхолдер.

Итог: в debug всё работает, в release **каждый** HTTP-запрос и WebSocket падает.
Сейчас это не видно только потому, что собирали debug.

### 1.2 Конфиг не переведён на HTTPS/домен
Проект переехал на `https://wiki.medcentralfa.ru` + nginx на 443 (`HTTPS_SETUP_INSTRUCTION.md`,
`backend/server.js:87-105` умеет TLS сам, но на бою TLS терминирует nginx — в корне лежит `certs.disabled`).
Мобилка по-прежнему ходит на IP по http. Плюс `src/services/vpn.js:22` хардкодит
`http://${VPN_SERVER_HOST}:9001/api/health` мимо `CONFIG.API_URL`.

Что нужно решить до кода: **проксирует ли nginx на 443 бэкенд и `/socket.io`?**
Если нет — надо добавить, потому что мобилке нужен один origin `https://wiki.medcentralfa.ru`:
- `https://wiki.medcentralfa.ru/api/...`
- `https://wiki.medcentralfa.ru/socket.io/` c `proxy_set_header Upgrade/Connection` (иначе WS не поднимется)
- `https://wiki.medcentralfa.ru/uploads/...` — сейчас `src/utils/avatarUrl.js` и `fixUrl()` в
  `ChatScreen.js:59` собирают URL картинок как `API_URL без /api` + путь; при переезде на домен
  это поедет автоматически, но только если раздача uploads тоже за nginx.

iOS: `Info.plist` имеет `NSAllowsArbitraryLoads=false` + `NSAllowsLocalNetworking=true` —
сейчас работает только потому, что 192.168.x.x попадает под local networking. По домену с валидным
сертификатом ATS будет доволен, отдельных исключений не потребуется.

### 1.3 Socket.IO вообще не аутентифицирован (безопасность, касается и веба)
`backend/server.js:127-142`:
```js
io.on('connection', (socket) => {
  socket.on('join', (userId) => {
    socket.join(`user:${userId}`);   // userId приходит от клиента, никто его не проверяет
```
Нет `io.use()` middleware, JWT не валидируется. Мобилка честно шлёт `auth: {token}`
(`src/services/socket.js:26`) — сервер этот токен **игнорирует**.

Любой, кто дотянется до порта, может подключиться, сделать `emit('join', <чужой userId>)`
и получать все чужие сообщения в реальном времени, плюс подделывать «печатает» и онлайн-статус.
После выноса сокета наружу через nginx/443 это перестаёт быть проблемой только LAN.

Чинить на бэке: `io.use((socket, next) => verify(socket.handshake.auth.token))`, `socket.userId`
брать из токена, а `join` игнорировать/принимать без аргумента.

## 2. Пуши — текущая схема нежизнеспособна

Сейчас: `notifee` рисует **локальные** уведомления по событию `new_message` из Socket.IO
(`src/services/notifications.js:123-135`), а сокет держится живым Android foreground-сервисом
(`App.tsx:25`, `notifications.js:74-93`). FCM/APNs нет ни в приложении, ни на бэке
(грепа по `fcm|firebase|apns|deviceToken` в `backend/` — ноль совпадений).

Что с этим не так, по возрастанию:

1. **`notifee.registerForegroundService()` не вызывается.** Notifee требует зарегистрировать
   таск (обычно в `index.js`, вне React-дерева) до показа уведомления с `asForegroundService: true`.
   В `index.js` его нет — сервис фактически не стартует как foreground.
2. **Тип сервиса — `shortService`.** В AAR notifee 9.1.8 сервис объявлен как
   `android:foregroundServiceType="shortService"`. При `targetSdk = 36` Android убивает
   shortService примерно через 3 минуты и не даёт его перезапустить сразу. То есть даже если
   починить п.1 — сокет в фоне живёт минуты, а не часы. Нужен `dataSync` + `FOREGROUND_SERVICE_DATA_SYNC`
   (а у dataSync с Android 14 свой лимит — 6 ч/сутки).
3. **В манифесте приложения нет `FOREGROUND_SERVICE`** (`AndroidManifest.xml` — только INTERNET,
   CAMERA, media, POST_NOTIFICATIONS, VIBRATE). Разрешение подтягивается мерджем из notifee,
   но полагаться на это при targetSdk 36 нельзя — нужен явный `FOREGROUND_SERVICE` +
   `FOREGROUND_SERVICE_DATA_SYNC`.
4. **iOS не получает ничего в фоне.** Foreground service — Android-концепция; `UIBackgroundModes`
   в Info.plist отсутствует. При сворачивании приложения сокет умирает → уведомлений нет вообще.
5. **Приложение убито → уведомлений нет** на обеих платформах.
6. **Mute не учитывается.** Бэкенд шлёт `new_message` всем участникам без оглядки на
   `isNotificationMuted` — веб фильтрует на клиенте (`SocketContext.js`, `mutedChatIdsRef`).
   Мобилка не фильтрует ничего → приглушённые чаты всё равно пушатся.
7. Уведомление приходит и когда пользователь **прямо сейчас открыл этот чат**.

**Рекомендация:** это единственная часть, где нужен не «допилить», а «переделать».
Правильная схема — FCM (Android + iOS через APNs-мост):
- таблица `user_devices (userId, token, platform, lastSeenAt)` + `POST /api/chat/devices` для регистрации;
- в `backend/routes/chat.js` рядом с `io.to(...).emit('new_message')` (строка 592) — отправка data-push
  тем участникам, у кого `isNotificationMuted = false` и кто сейчас офлайн (`onlineUsers` уже есть в `app.set`);
- на клиенте `@react-native-firebase/messaging` + notifee для отрисовки;
- foreground-сервис и вся возня с ним удаляются.
Побочный плюс: пуши перестают зависеть от того, дотянулся телефон до LAN/VPN или нет.

Если FCM по каким-то причинам нельзя (закрытый контур) — тогда честный вариант только Android,
с `dataSync` foreground-сервисом, явными разрешениями, `registerForegroundService()` и
запросом на отключение батарейной оптимизации. iOS в фоне при этом останется без уведомлений.

## 3. Функциональный разрыв веб → мобилка

Всё перечисленное уже есть на бэке и в вебе, в мобилке отсутствует.

### 3.1 Есть эндпоинт, мобилка его не зовёт

| Возможность | Бэкенд | В `mobile/src/services/api.js` | Используется в экранах |
|---|---|---|---|
| Закрепить чат | `PATCH /:chatId/pin` | нет | — |
| Порядок закреплённых | `PATCH /pins/reorder` | нет | — |
| Приглушить чат | `PATCH /:chatId/mute` | нет | — |
| Переименовать группу | `PATCH /:chatId/rename` | нет | — |
| Аватар группы | `POST/DELETE /:chatId/avatar` | нет | — |
| Массовое добавление | `POST /:chatId/members/bulk` | нет | — |
| Роль участника | `PATCH /members/:userId/role` | нет | — |
| Режим «только чтение» | `PATCH /members/:userId/readonly` | нет | — |
| Удалить группу | `DELETE /:chatId` | нет | — |
| Список ботов | `GET /chat/bots` | нет | — |
| Скрыть чат | `PATCH /:chatId/hide` | **есть** | **не вызывается** |
| Счётчик непрочитанных | `GET /unread/count` | **есть** | **не вызывается** |
| Кто поставил реакцию | `GET /messages/:id/reactions` | **есть** | **не вызывается** |
| Добавить/удалить участника | `POST/DELETE /:chatId/members` | **есть** | **не вызывается** |
| Выйти из группы | `DELETE /:chatId/leave` | **есть** | **не вызывается** |

По сути: **управления группой в мобилке нет вообще** — только создание (`NewChatScreen.js:64`).
Нет экрана «Информация о чате» / списка участников. Это самый большой кусок работы.

### 3.2 Socket-события, которые мобилка не слушает

| Событие | Где эмитится | Что теряется |
|---|---|---|
| `messages_read` | `chat.js:887` | Статус «прочитано». В `ChatScreen.js` вообще нет галочек — ни одной, ни двух. Веб использует `otherLastReadAt` (`Dashboard.js:305-315`) |
| `member_updated` | `chat.js:1406` | Не узнаёшь, что тебе выдали read-only. Отправка молча упадёт в 403 (`chat.js:523`) без внятного текста |
| `group_deleted` | `chat.js:1442` | Удалённая группа остаётся в списке и открывается |
| `new_release_note` | release-notes | Центр обновлений («Что нового») — целый модуль ver. 6.x, мобилки нет в нём совсем |

### 3.3 Ошибки, возникшие именно из-за расхождения

1. **Порядок чатов ломается на первом же сообщении.**
   Бэкенд сортирует `Ассистент → закреплённые по pinnedOrder → остальные по дате` (`chat.js:307-323`).
   `ChatListScreen.js:144-146` при `new_message` пересортировывает **весь список** по `lastMessageAt`,
   стирая и ассистента наверху, и закрепления.

2. **Новый чат не появляется в списке в реальном времени.**
   `ChatListScreen.js:130-143` делает `prev.map(...)` — обновляет только уже существующие элементы.
   Первое сообщение от нового собеседника не создаёт строку; появится только при перефокусе экрана.

3. **Мёртвый слушатель `message_edited`.** `ChatScreen.js:498` подписан на событие, которого
   бэкенд не эмитит никогда (в `chat.js` есть только `new_message`, `messages_read`,
   `member_updated`, `group_deleted`, `message_reaction_updated`).
   Правка и удаление сообщений вообще не рассылаются — это пробел и в вебе тоже,
   веб выкручивается перезагрузкой сообщений по `new_message`.

4. **Чат с Ассистентом не выделен.** Флаг `isAssistantChat` (`chat.js:288`) приходит, мобилка его
   игнорирует — бот выглядит как обычный собеседник и уезжает вниз по дате.

5. **`isReadOnly` не обрабатывается** — поле ввода активно, отправка падает с 403.

### 3.4 Мелочи, но заметные пользователю
- Нет бейджа непрочитанных на табе «Сообщения» (в вебе — бейдж в сайдбаре с поллингом раз в 10 с).
- Нет превью видео и PDF (веб: `videoPreview`, `pdfPreview` в `Dashboard.js:59-60`). В мобилке
  лайтбокс только для картинок (`ChatScreen.js:382`).
- Нет модалки «кто поставил реакцию» (веб: `components/chat/ReactionDetailsModal.js`).
- `chat.uploadFiles` в **вебе** (`frontend/src/services/api.js:272`) бьёт в `POST /chat/:chatId/upload`,
  такого роута нет — мёртвый код; веб реально грузит через `media.upload` (`Dashboard.js:424`).
  Мобилка бьёт в `POST /chat/upload` — правильный роут (`chat.js:475`). Формы ответа совместимы,
  но стоит унифицировать, чтобы дальше не разъезжалось.

## 4. Прочее по мобильному коду

- `android/app/build.gradle`: у `release` стоит `signingConfig signingConfigs.debug`. Для внутренней
  раздачи APK терпимо, но подпись debug-ключом означает, что обновление поверх сломается при смене
  машины сборки. Нужен свой keystore.
- `src/services/vpn.js` — заглушка, `vpnConfigured: false`. С переездом на публичный домен + HTTPS
  вопрос VPN может закрыться сам: если 443 доступен снаружи, WireGuard не нужен вовсе.
  Стоит определиться до того, как вкладываться в интеграцию туннеля.
- `src/store/authStore.js:31` — сокет коннектится только в `initialize()` (то есть при старте с
  сохранённым токеном). После **свежего логина** `loginComplete()` сокет не поднимает —
  до перезапуска приложения real-time не работает. Проверить и починить.
- В `notifications.js:129` `chatId` берётся как `data.chat?.id ?? data.chatId`; бэкенд шлёт
  только `data.chat.id` (`chat.js:592`) — второй вариант мёртвый, но безвредный.
- `App.tsx:41` — `useEffect` с зависимостью `[user]` (объект): при каждом `refreshUser()` объект
  новый → foreground-сервис и слушатели пересоздаются. Достаточно `[user?.id]`.

## 5. Предлагаемый порядок работ

**Этап 0 — расконсервация (полдня).** Решить судьбу `mobile/` в git. Поднять локально, убедиться,
что debug-сборка ещё собирается на RN 0.84.1.

**Этап 1 — сеть (1-2 дня).** Ответить на вопрос про nginx/443 (проксирование `/api`, `/socket.io`,
`/uploads`). Перевести `config.js` на `https://wiki.medcentralfa.ru`, убрать хардкод из `vpn.js`,
проверить release-сборку Android без cleartext и iOS с ATS. Заодно закрыть аутентификацию сокета
на бэке.

**Этап 2 — пуши (3-5 дней).** FCM + таблица устройств + отправка из `chat.js` с учётом mute и
онлайн-статуса. Выпилить foreground-сервис.

**Этап 3 — догнать веб по мессенджеру (5-7 дней).** Экран информации о чате с управлением группой,
закрепление/приглушение/скрытие в списке, `messages_read` + галочки, `group_deleted`/`member_updated`,
бейдж непрочитанных, ассистент наверху, починить сортировку и добавление новых чатов в список.

**Этап 4 — довести детали.** Превью видео/PDF, детали реакций, центр обновлений.
