# Database scaling controls

Пул PostgreSQL настраивается переменными окружения. Без них сохраняются прежние
значения, поэтому обновление приложения само по себе не увеличивает число
соединений.

| Переменная | По умолчанию | Допустимый диапазон |
| --- | ---: | ---: |
| `DB_POOL_MAX` | 10 | 1–200 |
| `DB_POOL_MIN` | 0 | 0–`DB_POOL_MAX` |
| `DB_POOL_ACQUIRE_MS` | 30000 | 1000–300000 |
| `DB_POOL_IDLE_MS` | 10000 | 1000–300000 |
| `DB_POOL_EVICT_MS` | 1000 | 100–60000 |
| `DB_CONNECT_TIMEOUT_MS` | 10000 | 1000–120000 |
| `DB_STATEMENT_TIMEOUT_MS` | 0 (выключен) | 0–600000 |
| `DB_READINESS_TIMEOUT_MS` | 3000 | 500–30000 |
| `DB_APPLICATION_NAME` | `alfa-wiki-<environment>` | строка |
| `RUN_BACKGROUND_JOBS` | `true` | boolean |
| `SOCKET_IO_REDIS_URL` | не задан | `redis://` или `rediss://` URL |
| `SOCKET_IO_REDIS_REQUIRED` | `false` | boolean |
| `SOCKET_IO_REDIS_CONNECT_TIMEOUT_MS` | 10000 | 1000–60000 |

Перед увеличением `DB_POOL_MAX` нужно учитывать все процессы приложения,
воркеры и резерв PostgreSQL:

```text
DB_POOL_MAX <= (max_connections - reserved_connections - worker_connections)
               / application_instances
```

`GET /api/health` проверяет, что процесс жив. `GET /api/ready` дополнительно
выполняет `SELECT 1` и возвращает состояние пула (`using`, `available`,
`waiting`, `max`). Балансировщик должен направлять трафик только на экземпляры
с успешным `/api/ready`.

При запуске нескольких backend-реплик только на одной нужно оставить
`RUN_BACKGROUND_JOBS=true`. На остальных необходимо установить `false`, иначе
Telegram-бот, синхронизации, напоминания и retry-задачи будут
запускаться дублированно.

Без `SOCKET_IO_REDIS_URL` Socket.IO сохраняет локальный in-memory adapter для
одиночного backend. Для нескольких реплик одинаковый Redis URL должен быть
задан на каждой из них. Если URL задан, но Redis недоступен, backend не запустится:
это защищает от незаметной потери межсерверных socket-событий.
В кластере также следует задать `SOCKET_IO_REDIS_REQUIRED=true`, чтобы ошибка
конфигурации не включила локальный adapter. Если клиенты Socket.IO используют
HTTP long-polling, на балансировщике дополнительно нужны sticky sessions.

## Состояние журналов на 2026-08-04

- `rb_activity_log`: 37 833 записи, диапазон 2026-05-12 — 2026-08-03;
  записей старше 90 дней нет.
- `page_history`: 70 816 записей; старше 180 дней только 74.
- Основной объём `rb_activity_log` находится в свежих JSONB-изменениях раздела
  `referrals`; PostgreSQL хранит их в TOAST, а списочный API поле `diff` больше
  не читает.

Автоматическое удаление журналов пока не включено: при текущем возрасте данных
оно почти не освободит место. Повторно оценить политику хранения стоит после
накопления 12 месяцев данных или при достижении `rb_activity_log` размера 1 ГБ.

## Порядок безопасной выкладки

Перед выкладкой убедиться, что на сервере установлен Node.js не ниже 18.19 и
сохранён свежий проверенный дамп PostgreSQL. Миграции 6.53 и 6.54 создают индексы
`CONCURRENTLY`, поэтому runner нельзя оборачивать во внешнюю транзакцию.

```bash
cd ~/projects/alfa-wiki/backend
npm ci
npm test
npm run migrate:safe-db:check
```

Код возврата `2` у первой проверки означает, что есть ожидающие миграции. Любой
другой ненулевой код требует остановить выкладку и изучить ошибку.

После остановки старого приложения и установки новой версии зависимостей:

```bash
npm run migrate:safe-db
npm run migrate:safe-db:check
```

Повторная проверка должна показать миграции 6.52–6.54 со статусом `applied`.
После запуска backend проверить:

```bash
curl --fail http://127.0.0.1:9001/api/health
curl --fail http://127.0.0.1:9001/api/ready
```

`/api/ready` должен вернуть `status: ready`, доступную БД и ожидаемый режим
Socket.IO. Для одной реплики допустим `memory`; для нескольких требуется Redis.

Проверка отката выполняется откатом версии приложения. Добавленные таблица и
индексы совместимы с предыдущим кодом и могут остаться в БД; удалять их во время
аварийного отката не нужно.

## Проверено на актуальном дампе

На дампе от 2026-08-04 (PostgreSQL 18.4) проверены восстановление, обнаружение
pending-миграций, применение 6.52–6.54 и повторный `--check`. Таблица
`service_consumables` создана, оба индекса имеют состояния `indisready=true` и
`indisvalid=true`. Backend успешно прошёл smoke-проверку `/api/health` и
`/api/ready` на восстановленной базе.

Frontend production build проходит с предупреждениями source map. После
разделения страниц по маршрутам стартовый JavaScript-бандл уменьшен примерно с
4.46 МБ до 274.49 КБ gzip. Тяжёлые редакторы, Excel/PDF-библиотеки, статистика и
административные разделы теперь загружаются отдельными чанками только при
переходе пользователя на соответствующий маршрут.

При выкладке frontend нельзя удалять старые хешированные файлы из
`build/static` до обновления активных клиентов: уже открытая вкладка может
запросить chunk предыдущей версии при позднем переходе на другой маршрут.
