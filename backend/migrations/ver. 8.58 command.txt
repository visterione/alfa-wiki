Применение миграции ver. 8.58 (модуль «Почта»).

ПЕРЕД ЗАПУСКОМ СДЕЛАЙТЕ РЕЗЕРВНУЮ КОПИЮ БАЗЫ — через админку портала, раздел
«Резервные копии».

Миграция только создаёт новое и ничего не трогает в существующих таблицах,
поэтому копия здесь — обычная предосторожность. Откатить можно вручную: DROP
четырнадцати таблиц с префиксом mail_ (через CASCADE) плюс DROP FUNCTION
mail_lexeme.

Из папки backend:

  npm run migrate:8.58:check     посмотреть, что уже на месте
  npm run migrate:8.58           применить


ЧТО НУЖНО СДЕЛАТЬ ДО ЗАПУСКА МОДУЛЯ

В .env добавить ключ шифрования паролей почтовых ящиков. Без него модуль не
поднимется — пароли негде будет взять.

  node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

Результат положить в .env:

  MAIL_SECRET_KEY=<64 шестнадцатеричных символа>

Ключ в репозиторий не попадает никогда. Если он потеряется, ящики придётся
заводить заново — расшифровать пароли будет нечем. Положите копию туда же, где
лежат остальные боевые секреты.

Необязательные переменные, у всех есть разумные значения по умолчанию:

  MAIL_MAX_CONNECTIONS=4      потолок одновременных соединений с reg.ru
  MAIL_SYNC_INTERVAL=180      секунд между кругами синхронизации
  MAIL_BODY_BATCH=50          сколько тел писем забирать за заход к ящику
  MAIL_STORE_PATH=...         где лежат сырые письма (по умолчанию backend/mail-store)
  MAIL_KEY_VERSION=1          версия ключа; нужна только при его смене
  MAIL_DAILY_SEND_LIMIT=200   суточный потолок отправки на ящик
  MAIL_DAILY_SEND_TOTAL=2000  суточный потолок отправки на всю сеть


ЧТО СОЗДАЁТ МИГРАЦИЯ

Четырнадцать таблиц:

  mail_accounts            ящики: координаты сервера, зашифрованный пароль, подпись
  mail_account_users       кому какой ящик открыт и что он в нём может
  mail_folders             папки ящика с UIDVALIDITY и курсором первичной заливки
  mail_messages            письма
  mail_addresses           справочник адресов
  mail_message_addresses   кто кому: от, кому, копия
  mail_message_bodies      тексты писем и поисковый вектор
  mail_attachments         вложения, включая вытащенный из них текст
  mail_user_message_state  личное поверх общего ящика: «я читал», «я взял в работу»
  mail_flag_ops            очередь отметок и удалений на отправку в IMAP
  mail_drafts              черновики и отправленное (по ним же считается предел)
  mail_saved_searches      сохранённые поиски, они же «умные папки»
  mail_audit               кто открыл, скачал, отправил, удалил
  mail_sync_runs           прогоны синхронизации — для разбора, почему ящик отстал

Плюс право доступа `mail` в adminAccess. Оно открывает администрирование
ящиков, но не сам раздел: видит ли человек почту, решает наличие доступа к
конкретному ящику, и только оно.

Функция mail_lexeme заводится модулем при первом поиске, отдельно её создавать
не нужно.


ПОЧЕМУ АДРЕСА ОТДЕЛЬНОЙ ТАБЛИЦЕЙ

Выглядит избыточно, но именно это даёт мгновенное «вся переписка с этим
человеком», автодополнение при ответе и работающий отбор по отправителю. Если
не разнести сразу, переделывать придётся с переиндексацией всей почты.


ПОЧЕМУ ПОИСКОВЫЙ ВЕКТОР СОБИРАЕТСЯ ДВУМЯ КОНФИГУРАЦИЯМИ

Русский стеммер несимметрично калечит фамилии: «Иванов» превращается в лексему
«иван», а «Иванову» — в «иванов». Это разные леммы, и поиск по фамилии в
именительном падеже не находил бы письмо, где она в дательном. «Гулиев» стеммер
и вовсе обращает в «гул», после чего письмо находится по слову «гулять».

Поэтому текст индексируется и конфигурацией russian (морфология обычных слов:
«договору» → «договор»), и конфигурацией simple без стемминга, а запрос по
второй части строится с префиксом: «иванов:*» находит «иванову», «иванова»,
«ивановым».

По той же причине точное попадание слова — первый ключ сортировки, а не
прибавка к весу. Прибавки не хватает: однокоренное слово может стоять в теме
(вес 1.0), а настоящее совпадение — в теле (вес 0.1), и десятикратная разница
весов перебивает любую разумную надбавку.


ПОЧЕМУ ОТМЕТКИ И УДАЛЕНИЯ УХОДЯТ ЧЕРЕЗ ОЧЕРЕДЬ

Флаг «прочитано» в IMAP общий на весь ящик, и пока часть сотрудников работает в
Roundcube, он — единственное, что у нас с ними общее. Не отдав его, мы оставим
им ящик, где вечно всё непрочитано.

Но отправка флага требует соединения с reg.ru, а их мало и они общие на сотню
ящиков: ждать свободного слота внутри HTTP-запроса — значит подвесить интерфейс
на действии, которое человек считает мгновенным. Поэтому отметка сразу ложится в
зеркало, а на сервер уезжает очередью. Круг синхронизации начинается именно с
неё: сначала отдать своё, потом забирать чужое. Наоборот нельзя — синхронизация
вернула бы прежний флаг и отменила действие человека у него на глазах.

Удаление идёт той же очередью, но письмо до подтверждения сервера не стирается,
а прячется (pendingDelete). Если стереть сразу, а сервер окажется недоступен,
письмо останется на reg.ru и при этом исчезнет из портала навсегда: обычная
синхронизация его не вернёт, она забирает только UID выше известного максимума.


ХРАНИЛИЩЕ ФАЙЛОВ

Сырые письма и вложения лежат в backend/mail-store, НЕ в uploads. Это
принципиально: uploads express раздаёт статикой целиком, и письмо стало бы
доступно любому, кто угадает ссылку, — а в ящиках переписка с пациентами.
Папка закрыта в .gitignore.

Место: около 44 ГБ на всю почту сети плюс распакованные вложения. На боевом
сервере свободно 1,4 ТБ, так что запас многократный. А вот на объём резервных
копий это влияет — посмотрите, что у вас попадает в бэкап.


ЧТО СДЕЛАТЬ ПОСЛЕ ВЫКАТА

Перезапустить бэкенд: Sequelize должен увидеть новые таблицы.

Ящики заводятся в админке портала: «Почта» → «Настройка ящиков» (адрес
/admin/mail, нужно право mail). Там же выдаётся доступ сотрудникам, проверяется
связь с сервером и виден журнал.

То же самое доступно из командной строки — сотню ящиков через форму заводить
никто не захочет:

  npm run mail:account -- --add --email info@alfa.ru --name "Регистратура"
  npm run mail:account -- --test info@alfa.ru
  npm run mail:account -- --grant info@alfa.ru --user ivanov --can-send
  npm run mail:sync -- --once --account info@alfa.ru
  npm run mail:account -- --list

Рабочий процесс синхронизации запускается отдельно от портала и должен работать
постоянно:

  npm run mail:sync

Отдельным процессом намеренно: соединения с чужим сервером висят открытыми, а
разбор архивной почты упирается в кривые кодировки и обрезанные вложения. Ни то,
ни другое не должно иметь возможности уронить вики. Без этого процесса почта
будет только показываться, но не обновляться, не отправляться и не удаляться —
очередь отметок разгребает он же.


ЧЕГО ЖДАТЬ ЛЮДЯМ

Кнопка «Почта» в панели быстрого доступа появится только у тех, кому выдан
доступ хотя бы к одному ящику. Остальные изменений не заметят: ни один
существующий раздел портала эта версия не затрагивает.

Что умеет: переключение между ящиками и папками, список с отбором, поиск по
всем доступным ящикам сразу (включая текст внутри PDF и DOCX), чтение письма и
переписки целиком, вложения, ответ, ответ всем, пересылка, черновики с
автосохранением, отметки «прочитано», «флажок» и «взял в работу», удаление с
доставкой до сервера, сохранённые поиски.

Чего нет намеренно: распознавания сканов (OCR) — отклонено заказчиком; создания
и переименования папок на сервере — вместо этого сохранённые поиски; массовых
рассылок — для них есть раздел «Маркетинг» со своим учётом предела и отпиской.
