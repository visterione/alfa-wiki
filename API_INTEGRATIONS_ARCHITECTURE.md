# Публичный API для внешних интеграций — архитектура

Документ описывает, как alfa-wiki принимает данные от сторонних систем (сайт клиники,
партнёры, сервисы) после перевода проекта на HTTPS.

Первая интеграция: **форма регистрации пациента с сайта клиники → сообщение в групповой
чат вики**.

---

## 1. Что уже есть в проекте

Транспорт «внешняя система → сообщение в чат вики» уже реализован и работает:

| Компонент | Файл | Назначение |
|---|---|---|
| Внутренний мессенджер | `models/index.js` (`Chat`, `Message`, `ChatMember`) | чаты, сообщения, realtime через Socket.IO |
| Telegram-совместимый Bot API | `routes/telegram-bot-api.js` | `/bot{token}/sendMessage` и ~40 методов |
| Токены ботов | `models/index.js` (`BotToken`) | токен, вебхук, привязка к User-боту |
| Простой приём уведомлений | `routes/notify.js` | АТС Comfortel шлёт `api_key + chat_id + text` |
| Управление ботами | `routes/bot-management.js` | CRUD ботов, выдача токенов, привязка к чатам |

Строить нужно не транспорт, а **публичный контур API** вокруг него: аутентификацию
интеграций, валидацию, хранение и надёжную доставку.

## 2. Периметр

**Это делается первым, до любого кода.**

### Что уже есть

nginx на боевом сервере стоит и настроен (конфиг `/etc/nginx/sites-enabled/alfa-wiki`,
в репозитории его нет): на 443 он раздаёт статику из `frontend/build` и проксирует
`/api/`, `/socket.io/`, `/uploads/` на `https://127.0.0.1:9001`. Ставить ничего не нужно,
нужно дописать правила.

### Проблема 1: порт 9001 слушает 0.0.0.0

`server.js` поднимает сервер на `0.0.0.0:9001`, то есть на бэкенд можно постучаться
напрямую с любого адреса, минуя nginx и все его ограничения.

**Решение** (безальтернативное, делаем в любом случае):
- закрыть 9001 на файрволе, оставив доступ только с `127.0.0.1`,
- либо `server.listen(PORT, '127.0.0.1')` в `server.js`.

Проверить, что после этого фронт, Socket.IO и загрузка файлов работают через 443.

### Проблема 2: через 443 наружу проксируется весь `/api/`

`/api/backup`, `/api/mis`, `/api/users`, `/api/salary-records` доступны из интернета.
Всё защищено JWT, но поверхность атаки — сотни эндпоинтов с зарплатами, паспортами
сотрудников и проксёй в МИС.

Что можно сделать, **зависит от того, ходят ли сотрудники в вики извне** (из дома,
с телефона, через мобильное приложение из `mobile/`):

**Вариант А — доступ только из клиник.** Ограничить `/api/` списком офисных
подсетей и VPN, публичным оставить только `/api/public/`:

```
Интернет ──▶ nginx (443)
              ├─ /api/public/*  ──▶ 127.0.0.1:9001   ← открыто всем
              └─ всё остальное  ──▶ allow офисные IP + VPN; deny all
```

**Вариант Б — сотрудники ходят откуда угодно.** Ограничение по IP сломает работу.
Тогда:
- `/api/` остаётся доступным, защита — JWT (как сейчас),
- добавляем rate limit на `/api/auth/login` (защита от перебора паролей),
- по IP закрываем точечно то, чем снаружи заведомо не пользуются: `/api/backup`,
  при желании `/api/mis`.

В обоих вариантах для `/api/public/` в nginx прописываем отдельный `location`:
лимит тела 100 KB, `limit_req` по IP, отдельный access-лог.

## 3. Публичный контур

Отдельный префикс, своя аутентификация, свои правила. С внутренним JWT-API не пересекается.

```
POST https://wiki.medcentralfa.ru/api/public/v1/forms/patient-registration
Headers:
  X-Api-Key: wk_live_...            обязательный
  Idempotency-Key: <uuid>           опциональный, для защиты от дублей при ретраях
  Content-Type: application/json
```

### Конвейер обработки

```
1. EDGE       nginx: TLS, лимит размера тела, connection rate limit
2. AUTH       X-Api-Key → ApiClient (+ проверка scope на конкретную форму)
3. THROTTLE   rate limit по ключу и по IP
4. VALIDATE   express-validator: схема формы, нормализация телефона и дат
5. PERSIST    запись в submissions (JSONB) — источник правды
6. DELIVER    форматирование + отправка ботом в чат, асинхронно, с ретраями
```

**Ключевое решение: сначала сохранить, потом доставить.** HTTP-ответ клиенту означает
«заявка принята и записана», а не «доставлена в чат». Если доставка упала — заявка
помечается `deliveryStatus = failed` и добивается крон-джобом. Сообщение в чате
не является единственной копией данных.

Раздел «Заявки» в интерфейсе вики **не делаем** (решение принято), но в БД пишем всегда:
это нужно для ретраев, дедупликации, аудита и восстановления, если сообщение удалят.

## 4. Модель данных

### `ApiClient` — интегрируемая система

Не пользователь, а внешняя система: сайт клиники, лендинг, партнёрский сервис.

```
id            uuid
name          'Сайт medcentralfa.ru'
keyType       'secret' | 'public'
keyPrefix     'wk_live_a1b2'      — для поиска строки и показа в админке
keyHash       sha256(полный ключ)  — сам ключ в БД не хранится
scopes        ['forms:patient-registration']
allowedOrigins text[]              — обязателен для keyType='public'
allowedIps     text[]              — опционально для keyType='secret'
rateLimit      int                 — запросов в минуту
isActive       bool
lastUsedAt     timestamptz
createdBy      uuid → users
```

Полный ключ показывается **один раз** при создании. Это отличие от `BotToken`,
который лежит открытым текстом — для нового публичного контура так не делаем.

**Два типа ключей**, потому что способ вызова со стороны сайта пока не определён:

- `secret` — вызывает бэкенд сайта. Ключ не покидает сервер. Основной режим,
  предпочтительный. Опционально дополняется IP-whitelist.
- `public` — вызывает JS формы прямо из браузера. Ключ виден в исходниках страницы,
  поэтому: обязательный `allowedOrigins`, обязательная капча на форме,
  жёсткий rate limit по IP, запрет на любые scope кроме приёма форм.

Один и тот же эндпоинт обслуживает оба режима; разница только в проверках middleware.

### `Submission` — универсальная заявка

Не таблица под конкретную форму. Форма №2 (запись на приём, обратный звонок, вакансия)
= новый валидатор + новый шаблон сообщения + строка конфига, **без миграции**.

```
id               uuid
formType         'patient-registration'
clientId         uuid → api_clients
payload          jsonb        — все поля формы как прислали (после нормализации)
status           'new' | 'in_progress' | 'done' | 'spam'
deliveryStatus   'pending' | 'sent' | 'failed'
deliveryAttempts int
deliveredMsgId   bigint       — id сообщения в чате
assignedUserId   uuid null
sourceIp         inet
userAgent        text
idempotencyKey   text unique null
createdAt        timestamptz
```

### `ApiRequestLog` — аудит

`clientId, method, path, statusCode, durationMs, ip, createdAt`.
**Без тела запроса** — там персональные данные.

## 5. Структура кода

```
backend/
  routes/public/
    index.js                          монтирует версии
    v1/forms.js                       POST /forms/:formType
  middleware/
    apiKeyAuth.js                     X-Api-Key → req.apiClient, проверка scope/origin/ip
    publicRateLimit.js                express-rate-limit по ключу и по IP
  services/public/
    formRegistry.js                   formType → { validator, formatter, targetChatId }
    forms/patientRegistration.js      схема 21 поля + шаблон сообщения
    submissionService.js              save → deliver → retry
  cron/
    submissionsRetryCron.js           добивает failed-доставки раз в минуту
  migrations/
    ver. X.XX add-public-api.sql
```

Монтаж в `server.js` — **до** внутренних роутов, со своим CORS (белый список origin,
а не текущий `origin: true`):

```js
app.use('/api/public', publicCors, publicRoutes);
```

## 6. Первая интеграция: форма регистрации пациента

### Эндпоинт

`POST /api/public/v1/forms/patient-registration`

### Поля

Схема выросла (41 поле и 8 файловых зон) и дублировать её здесь смысла нет —
единственный актуальный источник это **PUBLIC_API_PATIENT_FORM.md** и живой
`GET /api/public/v1/forms/patient-registration/schema`.

Устройство схемы в двух словах:

- `applicantType` (`self` / `child_parent` / `child_guardian`) — развилка всей формы.
  При `self` основной блок это пациент, иначе — представитель, а пациент лежит в `child*`;
- обязательность большинства полей условная (`requiredIf` в описании формы), поэтому
  «обязательное поле» имеет смысл только в паре с режимом анкеты;
- анкета приходит как `multipart/form-data`: к ней приложены СНИЛС, документы и,
  для `child_guardian`, нотариальная доверенность.

Enum'ы — строгие: свободный текст в этих полях не принимаем. Даты — в двух форматах,
`ГГГГ-ММ-ДД` и `ДД.ММ.ГГГГ`. Телефон и СНИЛС нормализуются на входе.

### Пример запроса

Полные примеры для обоих режимов — в PUBLIC_API_PATIENT_FORM.md.

### Ответы

| Код | Тело | Когда |
|---|---|---|
| 202 | `{ "ok": true, "id": "uuid" }` | принято и записано |
| 400 | `{ "ok": false, "error": "validation_failed", "fields": {...} }` | не прошло валидацию |
| 401 | `{ "ok": false, "error": "invalid_api_key" }` | ключ неверный или отозван |
| 403 | `{ "ok": false, "error": "scope_denied" }` / `origin_denied` | нет прав на эту форму / чужой origin |
| 429 | `{ "ok": false, "error": "rate_limited" }` | превышен лимит |
| 500 | `{ "ok": false, "error": "internal_error" }` | наша ошибка |

202, а не 200 — подчёркивает, что заявка принята к обработке, доставка в чат асинхронна.

### Сообщение в чате

В чат уходит **вся заявка целиком** (решение принято). Шаблон:

```
🆕 Новая заявка с сайта
Регистрация пациента · 24.07.2026 14:32

👤 Иванов Иван Иванович
Пол: мужской · Дата рождения: 12.03.1985
Семейное положение: женат

📄 Паспорт РФ 4510 123456
Выдан: ОУФМС России по гор. Москве
Дата выдачи: 20.05.2010 · Код: 770-001

🏠 117312, Москва, ЮЗАО, г. Москва
ул. Профсоюзная, к. 12, кв. 45

📞 +7 999 123-45-67
✉️ ivanov@example.com

ID заявки: 8f3a1c2e
```

Пустые необязательные поля в сообщение не попадают.

> **Персональные данные.** Сообщение остаётся в истории чата у всех участников
> навсегда и не ограничивается правами доступа. Состав участников группы должен быть
> минимальным и пересматриваться при кадровых изменениях.

## 7. Требования по персональным данным (152-ФЗ)

Набор полей — паспортные данные, адрес и контакты, то есть полноценные ПДн.

1. **Согласие на обработку** — обязательный чекбокс на форме сайта. Флаг и таймстемп
   сохраняются в `payload`; без него заявка отклоняется с 400.
2. **Не логировать тело запроса** — ни в morgan, ни в PM2-логи, ни в `ApiRequestLog`.
3. **Retention** — крон, обезличивающий или удаляющий `submissions` старше N месяцев
   согласно внутреннему регламенту.
4. **Только HTTPS** — форма на сайте и вызовы API.
5. **Узкий доступ к чату** — единственный механизм ограничения доступа в выбранной схеме.

## 8. Зависимости

Добавить один пакет:

```
express-rate-limit
```

Сейчас rate limiting отсутствует во всём проекте, включая `/api/auth/login` —
это стоит закрыть независимо от текущей задачи.

Валидация — уже установленный `express-validator`. Очередь сообщений не нужна:
«сохранить + попытаться доставить + крон-добивалка» покрывает ожидаемые объёмы.

### Отличия реализации от исходного проекта

- **Ограничение частоты — свой счётчик в памяти**, а не `express-rate-limit`.
  Бэкенд работает одним процессом (pm2 fork, Socket.IO требует единого состояния),
  общего хранилища не нужно, а новая зависимость означала бы `npm install` на боевом.
- **Валидация — свой движок по декларативной схеме** (`services/public/fieldValidator.js`),
  а не `express-validator`. Схема поля описывает и проверку, и нормализацию, и подпись
  для сообщения в чат — за счёт этого новая форма добавляется одним файлом.
- **Отправка сообщений ботом вынесена в `services/botMessenger.js`** и переиспользована
  в `routes/notify.js` (АТС Comfortel). Заодно там починилось обновление
  `lastMessage`/`lastMessageAt` — раньше чат с уведомлениями от АТС не поднимался
  в списке чатов.
