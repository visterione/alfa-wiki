# Глава 1. Обзор проекта

## Что такое Alfa-Wiki и зачем он существует

Alfa-Wiki — это внутренняя корпоративная платформа медицинского центра «Альфа». Её можно назвать интранетом: она работает только внутри сети организации (или через VPN) и решает задачи, которые возникают при управлении медицинским учреждением.

Проект начинался как вики-система — место, где сотрудники могут хранить инструкции, регламенты, описания процессов. Но со временем вырос в нечто значительно большее: сегодня это единая точка входа для десятков задач — от просмотра справочника услуг до расчёта зарплаты и обработки отзывов пациентов.

Такой рост типичен для внутренних корпоративных систем: начинаешь с малого, понимаешь что удобно иметь всё в одном месте, и постепенно добавляешь модули. Каждый новый раздел появлялся потому, что существующие инструменты (Excel-файлы, разрозненные сервисы, мессенджеры) не справлялись с потребностями организации.

---

## Какие задачи решает проект

Ниже перечислены все модули и их практическая ценность:

**Вики-страницы** — основа проекта. Врачи, менеджеры, администраторы могут создавать структурированные документы: инструкции по работе с оборудованием, регламенты, описания процедур. Страницы хранятся в папках с иерархией, поддерживают форматирование, таблицы, вставку медиа. Доступ к страницам можно ограничить по ролям.

**Чат** — внутренний мессенджер. Личные и групповые переписки. Специфика: некоторые участники — не люди, а боты, которые присылают системные уведомления. Это означает, что чат — это не просто «поболтать», а канал доставки важной информации: напоминания, оповещения о пропущенных звонках, уведомления о новых задачах.

**Канбан** — управление задачами. Несколько досок с разными командами и правами доступа. Задачи можно назначать, комментировать, прикладывать файлы, ставить дедлайны.

**Отзывы** — модуль обработки отзывов пациентов. Отзывы поступают с разных платформ (Яндекс, Google, ПроДокторов и т.д.) — вручную или автоматически через синхронизацию. Команда обрабатывает каждый отзыв по чёткому workflow с несколькими статусами, ролями и возможностью автоматизации.

**Курсы** — корпоративное обучение. Сотрудники проходят уроки, в конце — тест. Администратор видит статистику прохождения.

**Аккредитации** — учёт сроков аккредитаций врачей. Система автоматически присылает предупреждения за 90, 60, 30, 14 и 7 дней до истечения. Это критически важно: просроченная аккредитация — это юридические проблемы.

**Автопарк** — учёт транспортных средств, сроков страховки и ТО. Аналогично аккредитациям — автоматические напоминания.

**Анализы и услуги** — справочники цен из МИС (медицинской информационной системы Renovatio). Синхронизируются автоматически. Врачи могут смотреть актуальные цены, не заходя в МИС.

**Зарплата** — расчёт зарплаты врачей с учётом реферальных бонусов, бонусов за услуги, расходников, норм часов. Данные о фактических услугах тянутся из МИС.

**Карточки врачей** — публичные профили специалистов, которые отображаются на вики-страницах.

**Карта** — интерактивная карта с маркерами (например, расположение клиник, объектов).

**Телеграм-боты** — уведомления через Telegram и эмуляция Bot API для создания внутренних ботов.

**Почта** — рассылки сотрудникам через корпоративный SMTP.

## Как устроен проект технически (вид с высоты)

Проект состоит из трёх частей:

### Backend (сервер)

Node.js-приложение, которое запускается на сервере и работает непрерывно. Оно:
- Принимает HTTP-запросы от клиентов (браузер, мобильное приложение)
- Работает с базой данных PostgreSQL
- Управляет файловой системой (сохраняет загружаемые файлы)
- Интегрируется с внешними сервисами (МИС, Telegram, почтовый сервер)
- Рассылает push-уведомления через WebSocket
- Выполняет фоновые задачи по расписанию (cron)

Весь backend — один файл-точка входа (`server.js`) и куча файлов рядом с ним. Никаких микросервисов: всё в одном процессе.

### Frontend (браузерное приложение)

React-приложение — это то, что видит пользователь в браузере. Оно:
- Загружается один раз при открытии сайта
- Дальше переходы между страницами происходят без перезагрузки (это называется SPA — Single Page Application)
- Общается с backend через HTTP-запросы (REST API)
- Получает события в реальном времени через WebSocket

### База данных

PostgreSQL — основное хранилище всех данных: пользователи, страницы, сообщения, отзывы, задачи — всё. Файлы (изображения, документы) хранятся в файловой системе, в БД — только пути к ним.

## Как части взаимодействуют

Представь такую цепочку при загрузке страницы «Список пользователей»:

```
1. Ты кликаешь на "Администрирование → Пользователи" в браузере
2. React Router меняет URL на /admin/users
3. React рендерит компонент AdminUsers.js
4. AdminUsers.js при монтировании вызывает api.users.getAll()
5. Axios отправляет HTTP GET на http://192.168.22.39:9001/api/users
6. Express принимает запрос
7. authenticate middleware проверяет JWT-токен
8. requireAdminAccess('users') проверяет права
9. Route handler выполняет User.findAll() — SQL запрос к PostgreSQL
10. PostgreSQL возвращает строки
11. Sequelize преобразует их в JavaScript-объекты
12. res.json(users) — JSON уходит обратно
13. Axios получает ответ
14. setUsers(data) — React обновляет состояние
15. Компонент перерендеривается с новыми данными
16. Ты видишь таблицу пользователей
```

Весь этот путь занимает обычно 20-100 миллисекунд.

## Где что живёт физически

Сервер располагается по адресу `192.168.22.39` — это машина во внутренней сети медцентра. На ней:

- **Порт 9001** — backend Express + статика frontend (production mode)
- **PostgreSQL** — на том же сервере, стандартный порт 5432
- **Папка `/alfa-wiki/uploads/`** — все загруженные файлы
- **PM2** — запускает и контролирует Node.js-процесс

В development режиме (на твоём компьютере):
- Backend: `http://localhost:9001` (запущен через `node server.js` или PM2)
- Frontend: `http://localhost:9000` (React dev server с hot reload)

## Почему именно этот стек

Этот вопрос важен для понимания — не просто "так получилось", а почему именно Node.js + React + PostgreSQL.

**Node.js на сервере** — главное преимущество: можно писать на JavaScript и на сервере, и в браузере. Один язык — меньше когнитивной нагрузки. Node.js хорошо справляется с задачами нашего типа: много запросов, быстрые операции с БД, асинхронная природа хорошо ложится на HTTP-обработку. Для вычислительно тяжёлых задач (ML, видеообработка) Node.js — плохой выбор, но здесь таких задач нет.

**Express** — минималистичный HTTP-фреймворк. Не навязывает структуру, легко расширяется middleware. Для корпоративного приложения это удобно: полный контроль над тем, что происходит с каждым запросом.

**PostgreSQL** — мощная реляционная БД с поддержкой JSONB, массивов, полнотекстового поиска, UUID. Это не «просто хранить строки» — Postgres умеет многое из того, что раньше требовало отдельных инструментов (например, Redis для произвольных данных заменяется JSONB полями).

**React** — стандарт для сложных SPA. Компонентная модель, виртуальный DOM, огромная экосистема. Для приложения с таким количеством интерактивных элементов (редакторы, drag-and-drop, графики, real-time чат) — правильный выбор.

**Sequelize (ORM)** — позволяет описывать схему БД в коде и работать с данными через JavaScript-объекты. Плюс: не нужно писать SQL для стандартных операций. Минус: сложные запросы пишутся неудобно (иногда лучше сырой SQL). В проекте используется разумный баланс.

## Структура файлов — первое знакомство

```
alfa-wiki/
├── backend/          ← Всё что работает на сервере
│   ├── server.js     ← ТОЧКА ВХОДА. Запускай отсюда.
│   ├── routes/       ← Обработчики URL-запросов (44 файла)
│   ├── models/       ← Описание таблиц БД (index.js — всё в одном файле)
│   ├── middleware/   ← Проверки перед обработкой запроса (auth.js)
│   ├── services/     ← Бизнес-логика вынесенная из routes
│   ├── cron/         ← Задачи по расписанию
│   ├── migrations/   ← История изменений схемы БД
│   └── uploads/      ← Загруженные пользователями файлы
│
├── frontend/         ← React-приложение
│   ├── src/
│   │   ├── App.js    ← Корень приложения, здесь маршруты
│   │   ├── pages/    ← Компоненты-страницы (один файл = один маршрут)
│   │   ├── components/ ← Переиспользуемые компоненты
│   │   ├── context/  ← Глобальное состояние (Auth, Socket, Theme)
│   │   └── services/
│   │       └── api.js ← ВСЕ HTTP-запросы к backend идут отсюда
│   └── build/        ← Готовая сборка для production (не редактируй!)
│
├── docs/             ← Документация (ты здесь)
├── ecosystem.config.js ← Как запускать через PM2
└── logs/             ← Логи сервера
```

Главное что нужно запомнить: **backend и frontend — независимые приложения** в одном репозитории. У каждого свой `package.json`, свои зависимости. Backend не знает ничего о React, frontend не знает ничего о Sequelize. Они общаются только через HTTP и WebSocket.
