новых индекса для действующих горячих маршрутов выбраны планировщиком и активно

## 1. Backend и readiness

50 последовательных запросов к production readiness через локальный HTTPS:

| Метрика | Результат |
|---|---:|
| Average | 14.81 мс |
| p50 | 14.65 мс |
| p95 | 16.01 мс |
| p99 / max | 16.54 мс |
| Время проверки PostgreSQL внутри readiness | 1 мс |

p95 выше медианы только на 1.36 мс, или примерно на 9.3%. В этой выборке нет
длинного хвоста и заметных выбросов. Это synthetic-проверка readiness, а не
latency всех бизнес-маршрутов.

Состояние пула в момент проверки: `size=1`, `available=1`, `using=0`,
`waiting=0`, лимит `max=10`. Увеличивать пул сейчас не требуется.

## 2. Подтверждённый эффект новых индексов

Статистика накоплена после создания индексов, примерно за первые 32.4 часа.

| Индекс | Сканирований | В среднем | Прочитано записей индекса | Размер |
|---|---:|---:|---:|---:|
| `idx_chat_members_user_visible` | 62 975 | ~32.4/мин | 398 307 | 72 КБ |
| `idx_referral_bonuses_mis_user_clinic` | 337 | ~10.4/час | 2 340 577 | 6.7 МБ |

### Чаты

Индекс списка видимых чатов используется очень часто и имеет минимальный
размер. На один scan приходится в среднем 6.3 записи индекса. Это подтверждает,
что порядок полей `userId, isHidden, chatId` соответствует реальному запросу.

### Реферальные бонусы

Таблица содержит около **1 005 165 строк**. За один scan новый индекс читает в
среднем около 6 945 кандидатов, то есть примерно 0.69% таблицы. Планировщик
стабильно предпочитает индекс полному просмотру таблицы для соответствующего
фильтра.

Точный процент ускорения SQL определить нельзя без сохранённого baseline
`EXPLAIN ANALYZE`, но факт выбора и интенсивность использования обоих индексов
подтверждены production-статистикой.

### Расходники

Три индекса `service_consumables` пока имеют по 0 сканирований и занимают по
8 КБ. Модуль ещё не создаёт заметной нагрузки. Удалять индексы по данным одного
дня не нужно: их стоимость хранения и записи сейчас пренебрежимо мала.

Относительно дампа 2026-08-04:

- `rb_activity_log`: 37 833 → 38 319, прирост **486 записей** (+1.28%);
- `page_history`: 70 816 → 70 854, прирост **38 записей** (+0.054%).

Одного дня недостаточно для надёжной годовой экстраполяции. Retention пока не
нужен, но `rb_activity_log` следует повторно измерить через 30 дней.

`rb_excel_sources` выглядит необычно только по соотношению строк и размера.
Списочный API уже исключает `fileData`, а полный base64 загружается отдельным
endpoint, поэтому 403 последовательных сканирования восьми строк не являются
узким местом. На перспективу файлы лучше переносить в файловое/object storage,
но это не срочная задача.

## 5. Frontend и мобильные клиенты

После разделения кода по маршрутам стартовый JavaScript bundle уменьшился:

```text
до:     примерно 4.46 МБ gzip
после:  примерно 274.49 КБ gzip
выигрыш: примерно 93.8%
```

Это самый крупный непосредственно измеримый пользовательский эффект релиза:
меньше загрузка сети, парсинг JavaScript и потребление памяти на первом экране.

В access-log зафиксирован ответ `GET /api/chat` размером **215 133 байта**.
Один пример не показывает среднее значение, но маршрут стоит следующим
проверить на мобильном соединении. Он возвращает участников каждого чата и
данные последнего сообщения, поэтому payload растёт вместе с количеством чатов
и сотрудников.

## 6. Ограничения отчёта

Точный before/after p50/p95 бизнес-маршрутов сейчас недоступен:

- Nginx access-log не содержит `$request_time` и `$upstream_response_time`;
- Morgan хранится только в tmux history на 2 000 строк и не содержит стабильной
  суточной истории;
- расширение `pg_stat_statements` не установлено;
- до релиза не был сохранён baseline `EXPLAIN (ANALYZE, BUFFERS)`.

Поэтому отчёт не приписывает индексам неподтверждённый процент ускорения. Он
подтверждает здоровье системы и фактическое использование оптимизаций.

## 7. Следующие измерения

Без срочных изменений:

1. Добавить отдельный timing access-log Nginx с `$request_time` и
   `$upstream_response_time`.
2. После отдельной проверки включить `pg_stat_statements`.
3. Сохранять суточный агрегат p50/p95/p99, 5xx rate и размеров ответов.
4. Измерить `GET /api/chat` по количеству и размеру ответов.
5. Повторить размеры `rb_activity_log`, `mis_appointments` и
   `referral_bonuses` через 30 дней.

После появления этих данных следующий отчёт сможет показывать точные
before/after значения по каждому маршруту, а не только состояние системы и
выбор индексов.
